# dev-memory v2.0 设计规格

> **⚠️ 历史文档**：本文档为 v2.0 设计规格，当前版本为 v3.0。详见 [SKILL.md](../SKILL.md) 和 [README.md](../README.md)。

> 吸收 TRAE 记忆系统优点，从扁平六维结构升级为三层混合分层架构

## 1. 背景与动机

### 1.1 当前状态

dev-memory v1.3 采用扁平六维结构：单一 `DEV_MEMORY.md` 文件 + 按周归档。经过实际使用和与 TRAE 内置记忆系统的深度对比，发现以下不足：

- **缺少会话级索引层**：无法快速定位"某次讨论在哪"，只能翻六维记忆或归档
- **缺少消息级捕获**：仅在会话结束时六维提取，中间探索过程容易丢失
- **缺少用户级记忆**：每个项目重复记录相同的用户偏好
- **缺少引用频率追踪**：价值标记一旦评定不变，无法反映实际使用情况
- **触发优先级不足**：作为 Skill 在多数工具中处于最低优先级，不保证每轮触发
- **归档机制冗余**：如果有了完整的消息级记录，周归档的存在价值降低

### 1.2 TRAE 记忆系统的优势（可吸收部分）

TRAE 采用四层层级：用户级(`user_profile.md`) → 项目级(`project_memory.md`) → 会话级(`topics.md`) → 消息级(`session_memory_*.jsonl`)。

| TRAE 特性 | 是否吸收 | 说明 |
|-----------|---------|------|
| 四层层级 | 部分吸收 | 采纳项目级+会话级+消息级，用户级改为项目内 |
| 消息级 JSONL | 吸收 | 结构化捕获 intent/actions/outcome/learned |
| 会话级摘要索引 | 吸收 | 每日生成 Markdown 摘要，快速定位 |
| 引用频率淘汰 | 改良吸收 | 结合价值标记+引用计数，Dream 整理时参考 |
| 用户级记忆 | 改良吸收 | 放入项目目录，增加贡献者日志和设备溯源 |
| 时间目录组织 | 吸收 | sessions/ 按日期命名 |
| 20条上限自动淘汰 | 不吸收 | 保留追加式演进，不删除旧记忆 |
| 绑定安装目录 | 不吸收 | 保持可移植性，跟随项目走 |

### 1.3 不吸收 TRAE 的部分及理由

- **20条上限自动淘汰**：dev-memory 的核心原则是"旧记忆永不删除"，通过 Dream 整理(合并/去重/提升)而非删除来控制膨胀
- **绑定安装目录**：dev-memory 的核心价值是可移植性，所有文件跟随项目目录走
- **原生记忆系统**：dev-memory 不替代任何工具的原生记忆，而是作为项目级补充层

## 2. 架构设计

### 2.1 文件结构

```
项目根目录/
  dev-memory/                    ← 直接放在项目根目录
    CONFIG.md                    ← 配置文件（安装引导 + 隐私设置 + 工具注入指引，始终纳入 Git）
    DEV_MEMORY.md                ← 项目级六维记忆索引（默认 gitignore）
    USER_PROFILE.md              ← 项目级用户画像 + 贡献者日志 + 设备历史（默认 gitignore）
    SKILL.md                     ← 完整执行规范（可选本地副本，有下载地址则不需要）
    sessions/                    ← 会话级 + 消息级记录（默认 gitignore）
      2026-07-14.md              ← 当日会话摘要（Markdown，人类可读）
      2026-07-14.jsonl           ← 当日消息级记录（JSONL，机器可读，必选）
```

### 2.2 三层架构

```
┌─────────────────────────────────────────────────────┐
│ 第一层：项目级索引（DEV_MEMORY.md）                   │
│ 策展层 — 六维提炼后的高价值结论                        │
│ 类比：博物馆的精选展厅                                │
├─────────────────────────────────────────────────────┤
│ 第二层：会话级摘要（sessions/YYYY-MM-DD.md）           │
│ 导航层 — 每次会话的一段话摘要 + 上下文链接              │
│ 类比：博物馆的楼层导览图                              │
├─────────────────────────────────────────────────────┤
│ 第三层：消息级记录（sessions/YYYY-MM-DD.jsonl）         │
│ 原始层 — 每条消息的 intent/actions/outcome/learned     │
│ 类比：博物馆的完整档案库                              │
└─────────────────────────────────────────────────────┘

横向补充：
  USER_PROFILE.md — 跨会话的用户画像 + 贡献者溯源
  CONFIG.md       — 配置和工具注入指引（始终纳入 Git）
```

### 2.3 与 v1.3 的结构差异

| 维度 | v1.3 | v2.0 |
|------|------|------|
| 目录位置 | `docs/dev-memory/` | `dev-memory/`（项目根目录） |
| 文件层级 | 扁平（DEV_MEMORY.md + archive/） | 三层（DEV_MEMORY.md + sessions/MD + sessions/JSONL） |
| 归档 | `archive/YYYY-Www.md` 按周归档 | 取消，sessions/ 完整保留 |
| 用户画像 | 无 | `USER_PROFILE.md`（含贡献者日志+设备历史） |
| 消息级 | 无 | `sessions/YYYY-MM-DD.jsonl`（必选） |
| 会话摘要 | 无 | `sessions/YYYY-MM-DD.md` |
| SKILL.md 副本 | 建议放项目内 | 可选，有下载地址则不需要 |
| 执行步骤 | 8.5 步 | 7.5 步（移除归档步骤） |

## 3. 各文件详细设计

### 3.1 DEV_MEMORY.md（项目级六维索引）

保持 v1.3 的六维结构不变，增加两项：

**新增 1：引用计数标记**

每条记忆末尾增加 `[引用:N]` 标记，记录被后续会话引用的次数：

```markdown
- [2026-07-10 18:30] [★★★] 分诊+增量写入的节省足以覆盖双触发的成本 [引用:3]
```

引用计数在以下场景递增：
- 后续会话的六维提取中引用了该条记忆
- 后续会话的对比检查中发现与该条记忆相关
- Dream 整理时该条记忆被交叉引用

**新增 2：Dream 整理参考引用计数**

Dream 整理的"提升"操作增加引用频率判断：
- `★` 条目被引用 ≥3 次 → 提升为 `★★`
- `★★` 条目被引用 ≥5 次 → 提升为 `★★★`
- `★★★` 条目长期未被引用(>30天) → 标记 `[⚠️ 低引用]`，提示可能过时

**metadata 行更新**：

```markdown
> 最后更新: YYYY-MM-DD HH:MM | 会话: <session_id> | 指纹: 6维/N条/M更正/分数 | 最后整理: YYYY-MM-DD
```

移除了 `周归档: YYYY-Www`（取消归档制）。

**溢出处理（替代归档）**：

当主文件某维度条目超出上限时：
- 任务摘要 / 踩坑记录：上限改为 **8条**（v1.3 是 5条，因为不再归档，适当放宽）
- 探索路径 / 架构决策：上限改为 **5条**
- 最终结论 / 环境信息：上限改为 **8条**

超出的旧条目不移动到归档文件，而是：
1. 在条目前标记 `[~]` 表示"已溢出，详情见 sessions/"
2. Dream 整理时优先合并/去重溢出条目
3. 如果溢出条目长期未被引用(>30天)，在条目前标记 `[~⚠️]`

### 3.2 sessions/YYYY-MM-DD.md（会话级摘要）

每日一个文件，记录当天所有会话的摘要。格式：

```markdown
# 会话摘要 — 2026-07-14

## 10:52 — dev-memory 公开仓库创建 [session: 6a50bc3f]
用户要求创建不含记忆文件的公开仓库。完成了 orphan 分支创建和推送。
确认私有仓库保留记忆历史。
[续: 2026-07-10 dev-memory v1.3 升级]

## 14:30 — dev-memory v2.0 架构设计 [session: 6a55a2ee]
对比 TRAE 记忆系统，设计三层混合分层架构。确认方案 B + 寄生式注入。
[续: 10:52 公开仓库创建]
```

**设计要点**：
- 每个会话摘要 2-4 句话
- 包含 session_id 便于关联 JSONL
- `[续: ...]` 标注跨会话连续性，链接到上一次相关会话
- 按时间正序排列（最早在上）

### 3.3 sessions/YYYY-MM-DD.jsonl（消息级记录，必选）

每条消息一个 JSON 对象，一行一条。Schema：

```json
{
  "message_id": "6a55a2eef0e645bb36d55ae0",
  "timestamp": "2026-07-14 10:52:18",
  "session_id": "6a55a2eef0e645bb36d55adf",
  "intent": "用户要求创建公开仓库",
  "actions": [
    "检查私有仓库记忆文件状态",
    "创建 orphan 分支",
    "推送至 dev-memory-public"
  ],
  "outcome": "公开仓库创建成功，私有仓库保留记忆历史",
  "learned": [
    "orphan 分支可以创建无历史记录的干净初始提交",
    "git rm --cached 可取消已跟踪文件的追踪"
  ],
  "dimensions": ["①", "⑤"],
  "references": ["DEV_MEMORY.md ⑤条目: 隐私感知Git策略"]
}
```

**字段说明**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| message_id | string | 是 | 消息唯一标识 |
| timestamp | string | 是 | 精确到分钟 |
| session_id | string | 是 | 会话标识 |
| intent | string | 是 | 用户意图/请求（1句话） |
| actions | string[] | 是 | AI 执行的动作列表 |
| outcome | string | 是 | 结果（1-2句话） |
| learned | string[] | 否 | 学到的新知识/经验 |
| dimensions | string[] | 否 | 关联的六维维度编号(①~⑥) |
| references | string[] | 否 | 引用的 DEV_MEMORY.md 已有条目 |

**写入时机**：
- 每次"任务完成"硬触发时追加一条
- 每次"话题切换"硬触发时追加一条
- 分诊跳过时不写入

**与 TRAE JSONL 的区别**：
- TRAE 每条消息都记录（包括"等待用户回应"的中间状态）
- dev-memory 只在硬触发点记录（任务完成/话题切换），避免低价值消息膨胀
- dev-memory 增加 `dimensions` 和 `references` 字段，与六维索引联动

### 3.4 USER_PROFILE.md（项目级用户画像 + 溯源）

```markdown
# 项目用户画像

## 当前开发者偏好

- 沟通语言: Chinese
- 工作风格: 先高确定性组件，评估结果，再设计不确定部分
- 文件命名: yyyymmdd-hhmm 后缀
- 质量要求: 严谨，强调数据准确性和完整性
- 记忆管理: 自动保存，旧记忆保留，新记忆带时间戳

## 贡献者日志

| 时间 | 开发者 | 设备标识 | 会话ID | 变更摘要 |
|------|--------|---------|--------|---------|
| 2026-07-10 17:00 | JacobWu | DESKTOP-WJ2916 | 6a50bc3f | 初始化项目，创建 SKILL.md v1.0 |
| 2026-07-10 19:15 | JacobWu | DESKTOP-WJ2916 | 6a50bc3f | v1.3 升级：Dream+多工具适配+隐私 |
| 2026-07-14 11:00 | JacobWu | DESKTOP-WJ2916 | 6a55a2ee | v2.0 架构升级：三层分层+寄生注入 |

## 设备历史

### DESKTOP-WJ2916 (JacobWu)
- 首次使用: 2026-07-10
- 最后使用: 2026-07-14
- 工作内容: 项目全部开发（v1.0 ~ v2.0）

### [新设备 clone 后自动追加]
- 首次使用: YYYY-MM-DD
- 最后使用: YYYY-MM-DD
- 工作内容: ...
```

**设备标识获取方式**：
- Windows: `%COMPUTERNAME%`
- macOS/Linux: `hostname`
- 开发者名: `%USERNAME%` / `$USER`

**自动追加逻辑**：
- 每次会话开头检查时，读取 USER_PROFILE.md 的设备历史
- 如果当前设备不在列表中 → 追加新设备条目
- 如果当前设备在列表中 → 更新"最后使用"时间

**闭环逻辑**：

```
新设备 clone 项目
  → 读取 USER_PROFILE.md → 了解谁在什么设备上做过什么
  → 读取 DEV_MEMORY.md → 了解项目当前状态
  → 读取 sessions/ → 了解每次会话的详细过程
  → 开始工作 → 自动追加设备历史和贡献者日志
  → 会话结束 → 六维提取 + 会话摘要 + JSONL
  → push → 下一个设备继承完整记忆
```

## 4. 触发优先级：寄生式注入

### 4.1 问题诊断

调研确认，dev-memory 作为 Skill 在多数工具中处于最低优先级：

| 工具 | 优先级链 | dev-memory 当前位置 |
|------|---------|-------------------|
| TRAE | Rules(硬) > Memory(软) > Skills(按需) | Skills (最低) |
| Claude Code | 系统提示 > Auto Memory > CLAUDE.md > Skills | Skills (最低) |
| Cursor | 系统提示 > .cursor/rules(alwaysApply) | .mdc (高但仅注入上下文) |
| Codex | AGENTS.md > Memories(默认关) | AGENTS.md 引用 (高) |
| Windsurf | 系统提示 > .windsurf/rules(always_on) | .windsurfrules (高) |
| Cline | 系统提示 > .clinerules | .clinerules (高) |
| Copilot | 组织级 > 仓库级 > 个人级 | copilot-instructions.md (高) |

### 4.2 解决方案：薄 Rule + 厚 Skill

**策略**：将 dev-memory 的触发逻辑从 Skill 层提升到各工具的最高优先级层。

**薄 Rule**（始终加载，高优先级）：只写"何时触发 + 触发什么"，8-10 行
**厚 Skill**（按需加载）：完整执行流程（SKILL.md）

### 4.3 各工具注入方案

#### TRAE

**注入位置**：项目 Rules（project_rules）
**优先级**：硬性准则（最高，必须遵守）
**与原生 Memory 的关系**：Rules > Memory，dev-memory 的 Rule 优先级高于 TRAE 原生 Memory

注入内容（写入 TRAE 项目 Rules）：

```markdown
## 开发记忆规则（强制）

1. 对话开始时：静默读取 dev-memory/DEV_MEMORY.md 的 metadata 行和"当前状态概览"，
   检查时效性和会话去重。如文件不存在，标记"本轮需初始化"。
   同步检查 dev-memory/USER_PROFILE.md，如当前设备不在列表中则追加。
2. 任务完成时（代码推送/文件创建/测试通过等）：按 dev-memory/SKILL.md 执行记忆保存流程，
   包括六维提取、对比检查、增量写入、消息级 JSONL 追加、会话摘要更新。
3. 话题切换时：同上。
4. 分诊过滤：纯概念问答、单纯文件查看、闲聊未落地 → 跳过保存。
```

#### Claude Code

**注入位置**：项目级 `CLAUDE.md`（始终加载，用户指令层）
**优先级**：高（与 Auto Memory 并列注入，由模型仲裁，但 CLAUDE.md 是"用户指令"权重更高）
**与原生 Memory 的关系**：互补不冲突，Auto Memory 不保存 CLAUDE.md 已记录的内容

注入内容（追加到项目根目录 `CLAUDE.md`）：

### 4.4 全局生效方案

| 工具 | 全局配置文件 |
|------|------------|

```
注意：以下规则适用于所有项目。如项目内有 dev-memory/ 目录则自动生效，否则跳过。
```

### 4.5 三重触发保障

| 保障层 | 机制 | 成本 | 可靠性 |
|--------|------|------|--------|
| 第一重：开头检查 | Rule 注入，每轮首次响应时静默扫描 | ~100 token | 高（Rule 始终在上下文） |
| 第二重：中间检查点 | 每 5 轮对话轻量检查（~50 token），判断是否有新内容值得记录 | ~50 token/5轮 | 中（依赖 AI 遵守 Rule） |
| 第三重：Git hook | CONFIG.md 提供 `post-commit` hook 模板，commit 后提醒执行记忆保存 | 0 token（外部触发） | 最高（不依赖 AI） |

**Git hook 模板**（在 CONFIG.md 中提供）：

```bash
# .git/hooks/post-commit
echo "⚠️ dev-memory: 本次 commit 的变更已记录到 Git。"
echo "请确认 AI 已执行记忆保存流程（dev-memory/DEV_MEMORY.md + sessions/ JSONL）。"
echo "如未执行，请提醒 AI: '请按 dev-memory/SKILL.md 保存记忆'"
```

### 4.6 与各工具原生记忆系统的关系

| 工具 | 原生记忆 | 与 dev-memory 的关系 |
|------|---------|---------------------|
| TRAE | Memory (Rules > Memory > Skills) | Rules 注入 dev-memory 触发规则 > TRAE Memory 提供知识上下文。互补：TRAE Memory 存"是什么"，dev-memory 存"怎么做的" |
| Claude Code | Auto Memory + CLAUDE.md | CLAUDE.md 注入 dev-memory 触发规则。Auto Memory 不保存 CLAUDE.md 已记录内容，无冲突。互补：Auto Memory 自动捕获用户偏好，dev-memory 结构化保存开发过程 |
| Codex | Memories (默认关闭) | AGENTS.md 注入 dev-memory 触发规则 > Memories。如开启 Memories，两者互补 |
| Cursor | 无原生记忆 | .cursor/rules 注入 dev-memory。无冲突 |
| Windsurf | Memories (自动) | .windsurf/rules 注入 dev-memory 触发规则。Memories 自动记录对话重点，dev-memory 结构化保存。互补 |
| Cline | 无原生记忆 | .clinerules 注入 dev-memory。无冲突 |
| Copilot | 无原生记忆 | copilot-instructions.md 注入 dev-memory。无冲突 |

**核心原则**：dev-memory 不替代任何工具的原生记忆系统，而是作为项目级补充层。原生记忆存"是什么"（知识和偏好），dev-memory 存"怎么做的"（过程和决策）。两者互补不冲突。

## 5. 执行流程（7.5 步）

### 流程概览

```
开头检查（静默，Rule 注入保障）
  ↓
结尾触发（任务完成/话题切换/显式请求/安全网）
  ↓
Step 0: 多项目识别与记忆分发
  ↓
Step 1: 分诊 — 值得保存吗？
  ↓ 不值得 → 跳过
Step 2: 读取现有记忆（分层读取）
  ↓
Step 3: 提取本次会话六维记忆
  ↓
Step 4: 对比检查 — 更正与澄清 + 引用计数更新
  ↓
Step 5: 写入主文件 + 追加 JSONL + 更新会话摘要
  ↓
Step 6: 自我进化检查
  ↓
Step 6.5: 轻量 Dream 整理
  ↓
Step 7: 可见反馈
```

### 各步骤详细说明

#### 开头检查（静默）

与 v1.3 相同，增加：
- 检查 `dev-memory/USER_PROFILE.md`，如当前设备不在设备历史列表中，追加新设备条目
- 检查 `dev-memory/sessions/` 目录是否存在，不存在则创建

#### Step 0: 多项目识别与记忆分发

与 v1.3 相同，路径从 `docs/dev-memory/` 改为 `dev-memory/`。

#### Step 1: 分诊

与 v1.3 相同。

#### Step 2: 读取现有记忆（分层读取）

| 场景 | 读取范围 | 估计 token |
|------|---------|-----------|
| 开头检查 | DEV_MEMORY.md metadata + 状态概览 + USER_PROFILE.md 设备历史 | ~150 |
| Step 4 对比检查 | 各维度最新 1 条 + 历史更正记录 | ~500 |
| Step 2~6 完整执行 | 全量 DEV_MEMORY.md + 最近 1 天 sessions/MD | ~2500 |

#### Step 3: 提取本次会话六维记忆

与 v1.3 相同，六维结构不变。

#### Step 4: 对比检查 — 更正与澄清 + 引用计数更新

与 v1.3 相同，增加：
- 逐条检查新提取的记忆是否引用了已有条目 → 被引用条目的 `[引用:N]` 计数 +1
- 如果新记忆与 >14 天的旧记忆相关，主动检查旧记忆是否仍然有效

#### Step 5: 写入主文件 + 追加 JSONL + 更新会话摘要

**5.1 写入 DEV_MEMORY.md**（与 v1.3 的增量写入相同）
- 更新 metadata 行
- 更新"当前状态概览"
- 增量插入新条目（含 `[引用:0]` 初始标记）
- 追加历史更正记录

**5.2 追加 sessions/YYYY-MM-DD.jsonl**（新增）

生成一条 JSONL 记录，追加到当日文件末尾：

```json
{"message_id":"<id>","timestamp":"YYYY-MM-DD HH:MM","session_id":"<id>","intent":"...","actions":["..."],"outcome":"...","learned":["..."],"dimensions":["①","⑤"],"references":["DEV_MEMORY.md ⑤条目: ..."]}
```

如果当日文件不存在，创建新文件。

**5.3 更新 sessions/YYYY-MM-DD.md**（新增）

在当日会话摘要文件中追加本次会话的摘要：

```markdown
## HH:MM — <一句话标题> [session: <id>]
<2-4句话摘要>
[续: <上次相关会话的日期和标题>]
```

如果当日文件不存在，创建新文件并写入头部 `# 会话摘要 — YYYY-MM-DD`。

**5.4 更新 USER_PROFILE.md**（如果设备信息有变化）

更新贡献者日志和设备历史的"最后使用"时间。

#### Step 6: 自我进化检查

与 v1.3 相同（触发可靠性审计 + 记忆质量检查）。

增加检查项：
- 检查 JSONL 文件是否成功追加（文件存在且非空）
- 检查会话摘要是否成功更新

#### Step 6.5: 轻量 Dream 整理

与 v1.3 相同（合并/去重/提升），增加：

**引用频率提升**：
- `★` 条目被引用 ≥3 次 → 提升为 `★★`
- `★★` 条目被引用 ≥5 次 → 提升为 `★★★`
- `★★★` 条目 >30天未被引用 → 标记 `[⚠️ 低引用]`

**跨层合并**：
- 扫描 sessions/JSONL 中的 learned 字段
- 如果某个 learned 被多次独立记录 → 提升为 DEV_MEMORY.md 的 ④ 最终结论

**触发条件调整**（因为取消归档，Dream 更重要）：
- DEV_MEMORY.md 全维度条目总数 >24 条（原 20，因上限放宽）
- 距上次 Dream 整理 >7 天
- 历史更正记录 >5 条

#### Step 7: 可见反馈

与 v1.3 相同，增加 JSONL 和会话摘要的反馈：

```
📝 已更新项目记忆: <项目名> (<N>条新记忆, <M>条更正)[, 含 Dream 整理]
   健康度: 85/100 (新鲜✓ 覆盖✓ 密度⚠ 准确✓ 价值✓)
   会话记录: sessions/2026-07-14.jsonl (+1条), sessions/2026-07-14.md (+1段)
   → dev-memory/DEV_MEMORY.md
```
